# R20.4-SPECTRUM-CUDA1.26-FPS90-LOCKSTEP

## Objective

Make Spectrum and Waterfall feel materially smoother and force their steady-state presentation cadence to stay synchronized. The requested ceiling is about 90 FPS, while preserving real RF semantics: presentation may interpolate/scroll between source snapshots, but retained Waterfall history and measurement data still come only from real AstraRX FFT frames.

## Root cause found in CUDA1.25

The previous path had three independent timing domains:

1. `WebSocketClient` gated Spectrum and Waterfall separately at 16 ms (~60 Hz maximum).
2. Each `FftDisplayItem` owned its own 16 ms `QTimer`, so the two presentation clocks could start at different phases and drift/jitter independently.
3. QML and Max Hold could inject one-sided repaint requests, creating short render bursts that made one view report a different FPS from the other.

This could look jerky even when the average FPS numbers were similar.

## CUDA1.26 architecture

### 1. One shared presentation clock

`FftDisplayItem` no longer owns one presentation timer per item. Both native items register with a single process-lifetime `AnalyzerPresentationClock`.

Default request:

- `ISCAN_ANALYZER_PRESENT_FPS=90`
- 90 FPS -> ~11 ms precise timer cadence

Every shared tick invalidates both active analyzer items in the same GUI-thread turn.

### 2. Display-refresh awareness

The shared clock reads `QScreen::refreshRate()`.

The effective target is:

`min(requested analyzer FPS, physical display refresh rate)`

This is intentional. A 60 Hz panel cannot visibly show 90 unique frames; overscheduling the UI to 90 Hz on a 60 Hz panel only wastes CPU/GPU time and can make frame pacing worse.

Examples:

- 60 Hz display -> effective visual ceiling ~60 FPS
- 90 Hz display -> effective visual ceiling ~90 FPS
- 120 Hz display -> requested ceiling remains ~90 FPS

### 3. Lockstep source publication

Separate native source gates were removed.

Old:

- `ISCAN_SPECTRUM_FRAME_MS`
- `ISCAN_WATERFALL_FRAME_MS`

New default:

- `ISCAN_ANALYZER_FRAME_MS=11`

One `m_analyzerDisplayTimer` decides when to publish. On a due FFT message, that same acquired frame feeds both:

- Spectrum display frame
- Waterfall worker frame

Therefore Spectrum and Waterfall no longer select different AstraRX source snapshots because of separate elapsed timers.

### 4. Remove sustained one-sided paint bursts

Max Hold arrival no longer immediately repaints Spectrum. The next shared analyzer tick presents it.

QML `scheduleSpectrumPaint()` also invalidates Spectrum and Waterfall together. Standalone Waterfall repaint calls in the viewport/sample-rate path were removed.

### 5. 90 FPS interpolation tuning

Spectrum interpolation now uses the shared presentation interval as its lower bound rather than the old fixed 16 ms floor.

This prevents the old 60 Hz interpolation constant from adding unnecessary visual lag when the presentation target is ~90 Hz.

## What did not change

- CUDA kernel/plugin
- CUDA/CPU Waterfall worker architecture
- 8192 Spectrum display-bin default
- 2048 Waterfall worker-bin default
- 1024 retained Waterfall history rows
- Waterfall RF history semantics
- Max Hold data semantics
- RF calibration
- Manual Intensity scale behavior
- 3-second Spectrum divider hold
- Ice Blue PAN design and enlarged 44 px PAN height
- Scan / Memory workspace
- Frequency tuning behavior

## Runtime telemetry

### Real AstraRX FFT source cadence

```text
[FFT-SOURCE-5S] fps=... bins=...
```

This is the number of real RF snapshots arriving from AstraRX.

### Shared analyzer clock

```text
[ANALYZER-PRESENT-5S]
requestedFps=90
effectiveFps=...
tickFps=...
intervalMs=...
displayHz=...
items=2
```

### Actual native paint rate

Expect two lines over the same interval:

```text
[SPECTRUM-RENDER-5S] mode=spectrum  fps=... targetMs=... sharedClock=1
[SPECTRUM-RENDER-5S] mode=waterfall fps=... targetMs=... sharedClock=1
```

In steady state, Spectrum and Waterfall should be very close. Small measurement-window differences are acceptable; sustained multi-FPS divergence is not.

## Interpreting results

### Case A: displayHz ~= 60

A visible 90 FPS result is impossible without changing the display mode/panel refresh rate. Expected result is roughly 60 FPS for both views.

### Case B: displayHz >= 90, tickFps ~= 90, render FPS is much lower

The bottleneck is Qt Quick/QQuickPaintedItem/GPU presentation load, not the scheduler. The next optimization step should move more rendering from `QQuickPaintedItem/QPainter` to scene-graph-native geometry/texture rendering rather than increasing timer frequency again.

### Case C: render ~= 90 but FFT-SOURCE is lower

The UI should still look smoother because Spectrum interpolation and Waterfall fractional-row scrolling run at presentation cadence. However there are not 90 independent RF measurements per second; real RF time resolution is still the source FPS.

### Case D: Waterfall compute telemetry shows heavy coalescing

If `[SPECTRUM-COMPUTE-10S] coalesced=...` grows rapidly or row compute time approaches/exceeds the source period, Waterfall compute is the next bottleneck. Do not increase FFT bins or history copies to solve it.

## Build scope

Runtime files changed:

- `FftDisplayItem.h`
- `FftDisplayItem.cpp`
- `websocketclient.h`
- `websocketclient.cpp`
- `SpectrumGLPlot.qml`

CUDA plugin rebuild is **not** required.

The main `iScanMR10` application must be rebuilt because C++ and QML/QRC changed.

## Target validation

On Jetson, rebuild the main application and collect at least 20-30 seconds of:

```bash
./iScanMR10 2>&1 | tee /tmp/iscan-fps90.log

grep -E 'FFT-SOURCE-5S|ANALYZER-PRESENT-5S|SPECTRUM-RENDER-5S|SPECTRUM-COMPUTE-10S' /tmp/iscan-fps90.log
```

The primary acceptance condition is not only a high average number. It is:

1. Spectrum and Waterfall render FPS remain effectively equal.
2. Frame pacing looks smooth during live RF changes, zoom, and pan.
3. Waterfall does not clear on zoom/pan.
4. No regression in UI responsiveness.
5. CPU/GPU load remains sustainable during a soak test.
