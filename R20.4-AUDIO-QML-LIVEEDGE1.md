# R20.4 AUDIO/QML LIVEEDGE1 — 2026-09-17

## Scope
Surgical runtime hardening for two issues observed in the Jetson log:

1. Continuous `Audio queue overflow - dropped 1 old chunks` spam.
2. `QMLMap.qml: TypeError: Cannot read property 'updatedMs' of undefined`.

No RF/DSP/frequency/database/network behavior is changed.

## Audio change
`alsaaudioplayer.cpp/.h`

- restores the validated live-receiver defaults: 40 ms ALSA buffer, 10 ms period, 20 ms software staging, 8 queued chunks;
- when the high-water mark is reached, stale backlog is collapsed to half the queue limit in one operation instead of dropping exactly one packet forever;
- overflow diagnostics are aggregated to at most one message per 5 seconds;
- newest/live RF audio remains authoritative; stale speech is never replayed.

Expected diagnostic only when the system genuinely falls behind:

```
[AUDIO-LIVE-EDGE] dropped_stale_chunks= ... total_dropped= ... queue_chunks= ...
```

A healthy run should normally show no continuous AUDIO-LIVE-EDGE messages.

## QML map change
`iScreenDFqml/pages/QMLMap.qml`

`isDoaActive()` now treats a transient undefined ListModel row as inactive before accessing `updatedMs`. It also validates the numeric timestamp. This closes the Qt/QML model-lifetime race without changing DoA timeout semantics.

## Runtime validation
1. Start iScanMR10 and tune WFM/analog for at least 10 minutes.
2. Confirm the old per-packet `Audio queue overflow - dropped 1 old chunks` message is gone.
3. Listen for continuous audio; there must be no periodic gaps introduced by this revision.
4. Exercise spectrum tuning/dragging while audio plays.
5. Open/use the map/DoA view and confirm there is no `updatedMs of undefined` exception.
6. If `[AUDIO-LIVE-EDGE]` appears repeatedly every 5 seconds, capture `[AUDIO CONFIG]`, `[ALSA READY]`, the live-edge line, CPU load, and AstraRX packet rate; that indicates a real producer/consumer rate mismatch rather than a logging problem.
