# R20.2 Network + QML Lifetime Hardening (No Visual UI Change)

Date: 2026-09-09
Base: R20.1

## Trigger evidence

Target log reproduced:

- SIGSEGV signal 11 on the process/UI thread.
- fault address 0x100.
- Qt event `UpdateRequest` with receiver class `QQuickWindowQmlImpl...`.
- global checkpoint `AUDIO_WRITE`, but thread-local checkpoint `WS_BINARY_RETURN`, so the audio worker was active while the main/UI thread faulted later in Qt/QML event processing.
- entering the Network/5G page was followed by many `Audio queue overflow` messages.
- 5G reset emitted `TypeError: Cannot call method 'restart' of undefined` from Wifi5GPage.qml.

This matches the prior R16/R16.1 QML-lifetime crash family, and the R20.1 active source had regressed to executable JavaScript `.connect()` subscriptions in multiple QML files.

## Changes

### 1. Restore R16/R16.1 lifecycle-scoped signal handling

Removed executable JavaScript `.connect()` calls and replaced them with `Connections` objects in:

- SpectrumGLPlot.qml
- HomeDisplay.qml
- RadioScanner.qml
- FindBandsWithProfile.qml
- Setting.qml
- Wifi5GSetting.qml

The signal behavior is preserved; ownership/lifetime is now tied to the QML object that owns each `Connections` block.

### 2. Fix 5G Restarting completion handler

`cellularResetTimeoutTimer` is a QML id, not a property of `root`.

Changed:

- `root.cellularResetTimeoutTimer.restart()` -> `cellularResetTimeoutTimer.restart()`
- `root.cellularResetTimeoutTimer.stop()` -> `cellularResetTimeoutTimer.stop()`

This removes the runtime TypeError that could interrupt the Restarting -> Restart state cleanup.

### 3. Network LAN first-load no longer blocks the GUI/audio event loop

The Network Settings page previously called `NetworkController.loadAllLanConfig()` directly from QML on `Component.onCompleted`. That function performs live `nmcli device show` probing for multiple interfaces and can block the Qt GUI thread for seconds.

Added asynchronous NetworkController requests:

- `requestLoadAllLanConfig()`
- `requestLoadConfig(iface)`
- `requestDhcpInfo(iface)`

with result signals:

- `lanConfigReady(result)`
- `lanInterfaceConfigReady(iface, result)`
- `dhcpInfoReady(iface, result)`

Setting.qml now uses only the asynchronous path for these read-only queries.

### 4. WiFi config first-load moved to backend worker

`loadWifiConfig()` resolves the WiFi interface using `nmcli`, so it must not run synchronously in QML.

Added backend command:

- `wifi_config`

Wifi5GController executes it via the existing `runNetworkQuery()` worker and returns the same config data to QML.

### 5. 5G realtime status polling moved off main thread

`pollCellularRealtime()` previously called `cellularStatus()` synchronously from the QTimer callback on the Qt main thread.

R20.2 now:

- runs `cellularStatus()` in a short-lived worker thread,
- prevents overlapping realtime queries with `m_cellularRealtimeQueryInFlight`,
- publishes the result back through a queued invocation,
- discards stale results while reset/polling is suspended,
- avoids the duplicate immediate status query when `startCellularRealtime()` is called.

This keeps AstraRX WebSocket audio delivery responsive while the Network/5G page is open.

### 6. Wireless page loader incubation

Wifi5GSetting's inner Loader uses `asynchronous: true`, preventing first-time QML compilation/incubation from monopolizing the GUI thread. No layout, color, text, control, or navigation contract was changed.

## UI/UX preservation

No visual properties were changed in the modified QML files:

- no color changes
- no width/height changes
- no anchor changes
- no fonts
- no text labels
- no icons
- no visibility rules
- no control layout changes

The only loader change is asynchronous incubation to remove the first-open freeze.
