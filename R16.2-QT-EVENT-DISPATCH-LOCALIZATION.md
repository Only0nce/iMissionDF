# R16.2 Qt Event Dispatch Localization

## Evidence that triggered this revision

The R16.1 crash reported:

```
[R13-FATAL] ... checkpoint=209(WS_BINARY_RETURN)
thread_checkpoint=209(WS_BINARY_RETURN) ... addr=0x100 pc=<Qt5Qml + 0xB9A94>
```

This proves the WebSocket binary callback reached its final checkpoint before the
main/UI thread faulted. No bracketed Qt->QML FFT/SMeter/waterfall/frequency BEGIN
checkpoint replaced 209. The next localization boundary is therefore the Qt event
dispatcher itself (Timer, MetaCall, UpdateRequest, DeferredDelete, etc.).

## Change

`DiagnosticGuiApplication` subclasses `QGuiApplication` and brackets every
`notify(receiver,event)` call with allocation-free CrashDiagnostics state.
Application event behavior is unchanged: the original `QGuiApplication::notify()`
return value and exception behavior are preserved.

A fatal line now appends fields such as:

```
qt_event=43(MetaCall) event_receiver=0x... event_class=QObject event_depth=1 event_seq=12345
```

or:

```
qt_event=1(Timer) ... event_class=QQmlTimer
```

If it reports `qt_event=idle`, the fault occurred outside a Qt event delivery.

## Interpretation

- `Timer` / `QQmlTimer`: instrument the named QML timer callbacks next.
- `MetaCall`: inspect queued signal/invokeMethod delivery and identify the receiver.
- `UpdateRequest` / Qt Quick class: prioritize Canvas/render/update code.
- `DeferredDelete`: prioritize QObject/QML lifetime and deletion paths.
- `idle`: investigate non-event callbacks/native corruption instead.

No audio, WebSocket protocol, DSP, scanner, frequency, database, or UI behavior is
changed in R16.2.
